# 工作流：交付上线与维护

> **层级**：workflows（流程框架）· **适用阶段**：⑤交付 → ⑥上线前评估 → ⑦部署上线 → ⑧运营迭代。
> **引用源**：细则以 `core/通用研发协议.md` 为准（§五上线评估、§六运营合规、§十版本与资源、§十一状态沟通）；强制闸门见 `checklists/`。

## 本阶段做什么

把开发成果收口成**可验证的交付包**，逐项核对上线条件，把上线闸门交给人类。

| 动作 | 要点 | 依据 / 产出 |
|---|---|---|
| 1 交付自检 | 每轮改动按 `checklists/交付前检查.md` 逐条自检 | 交付前检查.md |
| 2 上线前评估 | 功能链路/权限安全/数据一致性/性能 + 三层对抗，逐项核对 | `checklists/上线前后检查.md`、协议§五 |
| 3 部署配置再确认 | 改动构建产物/入口/依赖/目录后，由 `general-deploy` 校验 `[deploy]` | 部署配置 gate |
| 4 交人类验收 | 附交付包（产物+测试证据+上线评估结论+人类平台操作清单），停在可部署态 | §五、§十.3 |
| 5 上线后核对 | 部署生效后逐项核线上可达性/安全冒烟/可观测回滚 | `checklists/上线前后检查.md` 上线后节 |
| 6 运营迭代 | 看数据定方向，回到需求与计划 | 协议§六 |

## 关键判断

- **上线由人类（项目所有者）把持**，AI 只提供证据与结论，不替代上线闸门（§十.3、上线前后检查.md 总则）。
- **可部署态判据**：阶段自检 + 交付前检查 + 自动化回归 + 探活冒烟 + 上线前后检查可上线。缺一项不得声称"可上线"。
- **验证缺口必须如实标注**"未测 + 原因 + 降级"，不把"构建通过"冒充"功能/安全验证通过"。

## 本阶段用哪份 checklist

- 每轮改动交付：`checklists/交付前检查.md`。
- 上线定版：`checklists/上线前后检查.md`（线上前 + 对抗测试 + 上线后核对）。
