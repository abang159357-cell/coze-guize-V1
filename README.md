# coze-guize-V1（通用研发协作规范仓库）

> 一套**不绑定具体技术栈**的通用研发协作与治理规范体系。让 AI 在明确目标、授权、验收标准的前提下，按适用的开发流程稳定工作、正确处理异常、提供可核实的交付证据；规则可长期维护、跨项目复用、版本可追踪。
>
> **先看 `INDEX.md` 用起来**：它把"遇到什么情况 → 读哪个文件 + 协议哪一节 + 用哪份 checklist"做完映射。

## 这是什么

> **定位（务必先读）**：本仓库是**可复制的 AI 协作规范模板库 + 平台实践沉淀库**，用于团队内部规范 / AI 协作引导 / 流程参考 / 知识沉淀。它**不是官方标准、不构成对外发布的正式制度、不替代官方文档**。借用的官方机制（`AGENTS.md` 长期记忆、`test_run` 验收、类型 skill）与平台硬约束依官方口径执行，见 `references/官方依据.md`；其余为团队规定与工程实践沉淀，可按需裁剪。

面向「AI 辅助软件开发」的规则底座，覆盖从需求到上线及后续维护的完整链路。它把官方提供的机制与纪律（`AGENTS.md` 长期记忆、`test_run` 验收、内置行为规范、各类型 skill）显式化、可裁剪、跨项目可复用，并补上官方未强制但项目需要的部分（运营合规、验收分级等）。每条规则有官方依据或长期实践支撑（见 `references/官方依据.md`）。

## 项目生命周期一站走通（主线）

> 看这一张图走完全程；各步依据/产出见下表。遵循官方协作模式：计划与验收部署由人类（项目所有者）掌舵，中间开发由 AI 无人值守推进。

```
①立项定需求 ──► ②计划定案 ──► ③无人值守开发 ──► ④推送+CI ──► ⑤交付自检 ──► ⑥上线前评估 ──► ⑦部署上线 ──► ⑧运营迭代
  人描述目标     人/AI定案        AI连续推进         按分支+PR     每轮改动          上线定版            项目所有者      看运营定方向
  (README)      (workflows/     (core/任务执行       (workflows/  (checklists/       (checklists/         (§十权限边界)   (协议§六运营合规)
                需求与计划)      与恢复)               Git与CI)    交付前检查)         上线前后检查)
```

| 阶段 | 负责人 | 依据/清单 | 产出 |
|---|---|---|---|
| ① 立项定需求 | 人类 | `workflows/需求与计划.md` | 明确的原始需求 |
| ② 计划定案 | 人类 + AI | 计划模式 + `templates/执行计划.md.template` | `docs/执行计划.md`（未定案不进下一步） |
| ③ 无人值守开发 | AI | `core/任务执行与恢复.md` + 协议§二§四 | 可部署产物 + 测试证据 + 交付包 |
| ④ 推送 + CI | AI | `workflows/Git与CI.md` | 按功能分支推 GitHub（PR 为审核/CI 单元）、CI 绿 |
| ⑤ 交付自检 | AI | `checklists/交付前检查.md` | 每轮改动通过交付检查（必须型） |
| ⑥ 上线前评估 | AI + 人类 | `checklists/上线前后检查.md` | 可验证的「是否可上线」结论 |
| ⑦ 部署上线 | **人类（所有者）** | 协议§十权限边界 | 线上服务对外可见 |
| ⑧ 运营迭代 | 人类 + AI | 协议§六运营合规 | 看数据定方向，回②迭代 |

**关键认知**：③的终点是「可部署上线状态」；⑤⑥ = ③ 的可部署态收口检查，不是必须全串行到部署的独立台阶。AI 在③内做完收口检查、达成可部署态后即停，交人类验收部署，不替代上线闸门。

## 如何使用（每个新项目三步）

1. **初始化时并进 AGENTS.md（登记规则基线）**：读 `templates/项目接入.md`，把 `core/通用研发协议.md` 与 `checklists/` 内容并在目标项目根 `AGENTS.md` 固定章节，并登记**规则基线**（来源仓库 `coze-guize-V1` + 协议版本 `V13` / commit，见 `VERSION.md`）。协议变更须经项目所有者确认后才生效、不自动覆盖既有基线。
2. **开发中遵守**：按 `core/任务执行与恢复.md` 推进，每轮改动交付前按 `checklists/交付前检查.md` 自检，改动核心逻辑时给出测试证据。
3. **上线前收口**：按 `checklists/上线前后检查.md` 逐项核对，通过后才交付。

> 涉及推送 GitHub / 接通 CI 的项目，另读 `workflows/Git与CI.md`；常用习惯可并入 `工作习惯.md`；检查本体系本身是否生效看 `规范验证.md`。

## 关键要点（一句话）

- **阻断即停**：同一问题最多凭证据试 1–2 次，无新证据就停、转做并行工作、如实报告。
- **复查须有据**：验证基于实际探测（输出/日志/页面/测试），不靠"推测应该没问题"。
- **真接通非 Mock**：真实调用不用假数据冒充成功。
- **正确性 ≠ 能编译**：可见改动必须在预览/运行时实际走通再声称完成。
- **最小确认点**：只在产品决策/不可逆/需授权处停下问人，其余连续推进。
- **多项目落地入口是 AGENTS.md**（官方必读机制），本仓库是它的"规则源"。

## 适用说明

- 适用：Web / 小程序 / App / 后端 / 脚本 / 库 / 自动化任务等任何技术栈与项目形态（不可预览类按 `references/平台专项规则.md`）。
- 不含：类型独有的开发细节（如 web 用 test_run、小程序用 coze CLI）——按对应类型 skill 执行，本仓库只收敛"通用"部分。各文档中的 `test_run` / `pnpm test` / `.coze` 均为 web/Node 类示例，非 web/Node 项目以对应类型 skill 的验收工具与配置为准。
- 与平台硬约束（端口 5000、pnpm/uv、`.coze` 落点、`sub_id` 不可改）冲突时，以平台约束为准。
- **局限**：本仓库是内部规范模板，**不构成对外合规背书或强制行业标准**；对外发布仍需按项目实际涉及的监管/安全要求另行满足。引用任何"官方依据"时，回到官方文档核对最新版（见 `references/官方依据.md` 核实基准）。

## 版本与变更

版本以 git commit 为准（见 `VERSION.md`）；改动规则/文件路径时，同步更新 `INDEX.md`、`AGENTS.md`、`README.md` 及 `VERSION.md` 依赖关系。
